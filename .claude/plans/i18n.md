# Internationalization (French + English)

## Context

Goal: add translation support so the app can ship in English (in addition to French), tied to the public-release effort (`public-release.md`) — an English-speaking audience on GitHub needs an English UI, not just an English README.

Findings from a full codebase pass (2026-08-11):

- **Greenfield i18n**: no i18n library, `locales/`/`messages/` dir, or translation abstraction exists anywhere. Every user-facing string is inline French, in JSX, template literals, and plain data objects.
- **App Router structure**: routes live under `src/app/` (not root `app/`), with one route group `(auth)` and one dynamic segment `baby/[babyId]`. No `[locale]` segment exists yet.
- **Next.js 16.2.10**: the middleware convention is renamed — this repo already uses `src/proxy.ts` exporting `proxy()`, not `middleware.ts`. It wraps Supabase's `updateSession()` (`src/utils/supabase/middleware.ts`), which does pathname-based auth redirects (`PUBLIC_PAGES`, `AUTH_ONLY_PAGES`, `ALWAYS_PUBLIC_PATHS`). Any locale-routing middleware must compose with this, not replace it.
- **Date/number formatting** hardcoded to French in ~10+ files: `date-fns/locale/fr` (calendar, feed, guess, admin, buy-list, anecdotes), and `Intl`/`toLocaleString('fr-FR', ...)` for currency (inventory) and dates (invitations, guess admin).
- **Strings live outside React components too**: login error messages passed through a URL query param (`src/utils/actions/login.ts`), push/in-app notification titles+bodies composed server-side and persisted to the `notifications` table + web-push payload across ~9 action files (`src/utils/actions/notify.ts` and callers), and static HTML email templates with manual `{{PLACEHOLDER}}` substitution (`src/utils/email.ts` + `public/emails/*.html`).
- **Data-as-copy files**: `src/utils/page_registry.ts` and `src/utils/notification-types.ts` store nav/label/description strings in plain objects, not JSX — need to become key-based.
- **Metadata**: one static `metadata` export in `src/app/layout.tsx` (no `generateMetadata` anywhere), plus `src/app/manifest.ts` (PWA manifest) — both static French.
- **Scope**: ~100 files under `src/` contain hardcoded French copy. This is a large, mechanical migration on top of a smaller architectural core (routing, middleware, formatting helpers).
- **Second-pass findings**: no `zod` usage anywhere (validation is manual, inside server actions — folded into the Phase 2.2/3 sweep for hardcoded error strings), and no `error.tsx`/`not-found.tsx`/`loading.tsx`/`global-error.tsx` exist yet in `src/app/` (not a current gap, but any added later need locale-aware strings from day one). `.github/workflows/ci.yml` already exists (typecheck + lint + docker build, no test step) — see Phase 5. `public/sw.js` has hardcoded French push-notification fallback strings that need special handling since it's a static file outside React/next-intl — see Phase 4.3. ~12 imperative `sonner` `toast(...)` call sites across 6 files carry hardcoded French and won't surface in a plain JSX-text grep — see Phase 3.3. Verified next-intl fully supports Next 16's `proxy.ts` rename and this repo's named-export style.

## Decisions (recommended defaults — flag if you want different)

1. **Library: [next-intl](https://next-intl.dev/)**. It's the standard for App Router, handles locale routing, `generateMetadata`, message loading, and works from Server Components/Actions (needed for the notification/email cases below). Rolling a custom solution isn't worth it at this scope.
2. **Locales: `fr` (default) + `en` at launch, designed to extend beyond two.** The user anticipates adding more languages later, so locale-specific code should read from a single shared `locales` array (`src/i18n/config.ts`, see Phase 1) rather than being hardcoded to a two-way `fr | en` choice — e.g. avoid `locale === 'fr' ? x : y` branches in favor of `messages[locale]`/keyed lookups, so a third locale is a new message file + a `date-fns` locale import, not a code change. This affects Phase 2.1's formatting helper and Phase 3.2.iii's `page_registry.ts`/`notification-types.ts` refactor specifically (see updates there).
3. **No URL-based locale routing.** Locale is never encoded in the URL — no `/fr/...`/`/en/...` prefix, no `[locale]` route segment, no `src/app/` restructuring, no merging routing logic into the existing Supabase auth `proxy.ts`, and no need to swap `next/link`/`useRouter`/`usePathname` for locale-aware wrappers anywhere in the codebase.
4. **Locale is fixed per deployment — one value, `DEFAULT_LOCALE`, no per-user override.** (Revised — see history below.) There is no `NEXT_LOCALE` cookie, no `profile.locale` column, no in-app language switcher, and emails/push notifications don't need per-recipient translation — every string in the app (UI chrome *and* async messages) resolves against the single `DEFAULT_LOCALE` env var, read server-side, following the exact runtime-config pattern `SITE_URL`/`VAPID_PUBLIC_KEY` already use (commit `554423c`). Add it to `.env.local.example`, `.env.docker.example`, `mise.toml.example`'s `[env]` block, and `docker-compose.portainer.yml`, alongside those. One Docker image, redeployed with `DEFAULT_LOCALE=en` instead of `fr`, serves an English-only instance — no rebuild needed, no per-user state to manage.

   *Why not per-user locale (what the plan originally had)*: the user pointed out that this app's content — post captions, "pronostic" guesses, comments — is itself user-generated text in a single language per family, not translatable UI copy. Letting individual family members pick their own UI language would produce pages where the chrome is in one language and the actual content sits in another, which is more confusing than helpful. A deployment (== a family) speaks one language; the UI should match. This also removes the trickiest part of the original plan entirely: no `profile.locale` DB migration, no settings UI, and Phase 4's notification/email fan-out no longer needs to resolve a locale per recipient — it's always the one deployment-wide value.

   *Revision history, for the routing decision (§3) specifically*: an earlier draft used `localePrefix: 'as-needed'` (French unprefixed, English at `/en/...`), which broke once the default needed to be a runtime env var rather than hardcoded — `'as-needed'` needs the client bundle to know which locale is "default" to decide whether to omit the URL prefix, and that value gets baked into the static JS at `next build` time, reintroducing the exact build-time/runtime mismatch bug commit `554423c` fixed for `SITE_URL`/`VAPID_PUBLIC_KEY`. Switching to `localePrefix: 'always'` fixed that but still required the full `[locale]` route restructuring. Dropping routing entirely (once it became clear there's no per-user or per-visitor need for a URL-visible locale at all) removed the problem at the root.
5. **Rollout order: infra + critical path first, long tail after.** Given the stated urgency ("need it in English to ship"), Phase 1–2 (below) makes the *whole app* structurally translatable, and Phase 3 translates the highest-traffic flows first (auth, nav, baby hub, feed) so you can flip a switch and demo/ship in English, then keeps going through the rest (calendar, guess, admin, buy-list, inventory, settings, emails, notifications) as follow-up work rather than one giant PR.

## Phase 1 — Foundations (no routing needed)

`src/app/` structure, `proxy.ts`, and every existing `next/link`/`next/navigation` import are untouched by this phase — see Decisions §3.

1. `pnpm add next-intl`.
2. Create `src/i18n/config.ts`: `export const locales = ['fr', 'en'] as const; export type Locale = (typeof locales)[number];` — the single shared source of truth for the locale list (Decisions §2), consumed by `request.ts`, the Phase 2.1 formatting helper, and anywhere else that needs to know the supported locales without hardcoding them.
3. Create `src/i18n/request.ts`: `getRequestConfig(async () => { const locale = (process.env.DEFAULT_LOCALE as Locale) ?? 'fr'; return { locale, messages: (await import(\`../../messages/${locale}.json\`)).default }; })` (or split by namespace — see Phase 3.1). No cookie, no per-request variation — `DEFAULT_LOCALE` is read directly here, server-side only, in a file that's never imported by client-bundled code, so there's no build-time/runtime mismatch risk to design around.
4. Wrap `next.config.ts` with `createNextIntlPlugin()`.
5. Add `DEFAULT_LOCALE` (plain runtime env var, e.g. `DEFAULT_LOCALE=fr`) to `.env.local.example`, `.env.docker.example`, `mise.toml.example`'s `[env]` block, and `docker-compose.portainer.yml`'s `environment:` block, next to `SITE_URL`/`SUPABASE_URL`/etc. — same file set commit `554423c` touched for the SITE_URL/VAPID runtime-config migration.
6. `<html lang="fr">` in `src/app/layout.tsx` → set dynamically from `getLocale()`.
7. **Wrap `src/app/layout.tsx`'s children in `NextIntlClientProvider`** (passing `messages` from `getMessages()`) — without this, `useTranslations()` in Client Components (most of the interactive UI: forms, feed, calendar) won't have access to messages at all. Easy to miss since server-side `getTranslations()` works fine without it, so the gap wouldn't surface until the first Client Component migration in Phase 3.
8. Verify: `pnpm typecheck && pnpm build`, confirm the app still renders identically (same URLs, same routes) with `DEFAULT_LOCALE=fr` — this phase should be invisible until Phase 3 starts actually calling `useTranslations()`/`getTranslations()` somewhere.

## Phase 2 — Shared infrastructure for non-component strings

1. **Formatting helper** (`src/utils/formatting.ts`): `getDateFnsLocale(locale: Locale)` (using the `Locale` type from `src/i18n/config.ts`, Phase 1 — not a separately hardcoded `'fr' | 'en'` union) doing a keyed lookup into a `Record<Locale, DateFnsLocale>` map (`{ fr: frLocale, en: enUS }` today, extendable by adding a key), and a `formatCurrency(amount, locale)` wrapper around `Intl.NumberFormat` mapping each locale to its BCP-47 tag (currently hardcoded `'fr-FR'`/`EUR` in inventory — note currency itself may eventually need to be independent of locale, but that's out of scope for this pass). Every hardcoded `date-fns/locale/fr` import and `'fr-FR'` `Intl`/`toLocaleString` call (calendar, feed, guess, admin, buy-list, anecdotes, inventory, invitations — ~10+ files) gets swapped to call this helper with `getLocale()` (server) — since locale is deployment-wide, not per-request, this can even be read once and threaded through rather than re-resolved per component, but `getLocale()`/`useLocale()` work fine either way and keep the code uniform with the rest of the i18n calls. Leave `src/utils/actions/notify.ts`'s `Intl.DateTimeFormat('fr-FR', { timeZone: 'Europe/Paris', ... })` alone — that's quiet-hours business logic tied to the household's timezone, not a display string.
2. **Server-generated strings**: `src/utils/actions/login.ts`'s error message (currently built into a URL query param) should be resolved server-side via `getTranslations()` before building the redirect URL, using the fixed deployment locale — much simpler than the original per-request-locale version of this step, since there's no request-specific locale to resolve. This is one instance of a broader pattern worth sweeping for in Phase 3: server actions that return/throw hardcoded French error strings (e.g. `catch (err) { throw new Error("Erreur lors de ...") }`), since several toast call sites (see Phase 3.3) fall back to `err.message` when it fails — so the fallback text is only half the fix; the thrown message itself needs translating too.

## Phase 3 — String extraction (incremental, section by section)

3.1. Decide message file layout: namespace by feature (`common`, `auth`, `nav`, `feed`, `calendar`, `guess`, `admin`, `buyList`, `inventory`, `anecdotes`, `settings`, `profile`, `notifications`, `emails`) inside `messages/fr.json` / `messages/en.json`, rather than one flat file — keeps diffs scoped per section as you migrate incrementally.

3.2. Order (critical path first, per the rollout decision above):
   1. Shared chrome: `_header/`, `_home/landing.tsx`, root `layout.tsx` metadata (`generateMetadata` replacing the static `metadata` export, using `getTranslations`/`getLocale` — works the same with or without routing). `src/app/manifest.ts` (PWA manifest) stays French-only for now — low priority, no locale-driven variant without routing to key off (could read the `DEFAULT_LOCALE` env var directly if ever needed).
   2. Auth flow: `(auth)/login`, `signup`, `forgot-password`, `reset-password`, `invite`, `src/components/login-form.tsx` and sibling form components.
   3. `page_registry.ts` and `notification-types.ts` → convert from literal-string objects to translation-key objects (a `labelKey`/`descriptionKey` string resolved via `t()` at the call site), not a `{ fr: '...', en: '...' }` inline map — the former scales to N locales via the message files alone, the latter would need a code change per new locale.
   4. `baby/[babyId]/page.tsx` (hub) and `onboarding/`.
   5. `feed/` (largest section, ~14 files).
   6. `calendar/`, `guess/` (+ `admin/`), `admin/`.
   7. `buy-list/`, `inventory/`, `anecdotes/`.
   8. `profile/`, `settings/`.

3.3. Mechanical rule per file: replace inline JSX text and template-literal copy with `useTranslations()` (client) / `getTranslations()` (server) calls — no navigation imports need to change, since there's no locale-aware routing (Decisions §3). **Also grep for imperative `sonner` `toast(...)`/`toast.success(...)`/`toast.error(...)` calls specifically** — these carry hardcoded French title/description/button-label text (confirmed in ~12 call sites across 6 files: `settings/_components/baby_settings_card.tsx`, `settings/_components/account_card.tsx`, `_header/notification_bell.tsx` — this one also has button `label`s inside the toast's action config, easy to miss — `admin/_components/display_page_settings.tsx`, `admin/_components/display_bug_reports.tsx`, `admin/_components/display_users.tsx`) and won't show up in a plain JSX-text sweep since they're function calls, not markup.

## Phase 4 — Emails and push/in-app notifications

Since locale is fixed per deployment (Decisions §4), this phase is much simpler than a per-recipient design would be: every email and notification uses the one `DEFAULT_LOCALE` value, same as the rest of the app — no per-recipient resolution, no `createTranslator` fan-out loop.

1. **Emails** (`src/utils/email.ts`, `public/emails/*.html`): duplicate each template into `public/emails/fr/*.html` and `public/emails/en/*.html` (translated copy, same `{{PLACEHOLDER}}` substitution mechanism — no need to introduce a templating engine for this). `email.ts` picks the template folder + subject line from `process.env.DEFAULT_LOCALE`, resolved once, not per-recipient. Check whether Supabase's own auth emails (confirmation/magic-link/recovery/email-change) are configured in this repo or in Supabase project settings — if the latter, that's a separate, non-code change to flag back to the user rather than something this plan can implement.
2. **Push/in-app notifications** (`src/utils/actions/notify.ts` + ~9 callers: `posts.ts`, `comments.ts`, `join-baby.ts`, `circles.ts`, `events.ts`, etc.): change call sites to pass a translation key + params instead of a literal title/body string; `notifyUsers()` resolves the title/body once via `getTranslations()` against the deployment locale and sends the same payload to every recipient — the existing "compose once, send to all" shape doesn't need to change structurally, just the string source.
3. **`public/sw.js`'s push fallback strings**: `public/sw.js:6-7` hardcodes French fallbacks (`data.title || "Le petit monde"`, `data.body || "Il y a du nouveau !"`) shown if the push payload is missing a title/body. This file is a plain static asset served outside Next.js/React — it can't import next-intl or read messages at request time. Since it's static, the fallback strings could in principle be generated per-locale at build/deploy time to match `DEFAULT_LOCALE`, but given Phase 4.2 already guarantees every real payload carries a translated title/body, this fallback only fires on a malformed payload (a bug, not a normal path) — leave it as a neutral last-resort rather than spending effort localizing it.

## Phase 5 — QA and rollout

- `pnpm typecheck && pnpm lint && pnpm build` after each phase, not just at the end.
- Manually test in both locales by restarting the dev server with `DEFAULT_LOCALE=fr` and then `DEFAULT_LOCALE=en`: signup → login → baby hub → feed → calendar → settings, plus at least one email (invite) and one push notification in each locale — confirming the whole app (not just partial state) reflects the env var with no leftover hardcoded strings.
- PWA install/manifest is unaffected by this plan (URLs never change), no extra verification needed there.
- Commit per CLAUDE.md conventions — small, scoped commits per subtask (e.g. `feat(i18n): add next-intl config and provider`, `feat(i18n): translate auth flow`, `feat(i18n): translate feed section`), CHANGELOG.md updated after each.
- `.github/workflows/ci.yml` already exists (`typecheck-and-lint` job: install → `pnpm typecheck` → `pnpm lint`, plus separate docker build jobs, no test step). Add a lightweight key-sync check for `messages/fr.json`/`messages/en.json` (a small script asserting both files have the same set of keys, run right after `pnpm lint`) so a translation gap fails CI instead of shipping silently missing English strings.
- Once a phase is fully done and verified, this file gets a `## Status: implemented` header noting what shipped and any deviations, then moves to `.claude/plans/done/` — likely in stages (Phase 1–2 done first, Phase 3 sections checked off incrementally, Phase 4 last) rather than all at once given the size.

## Decisions log

1. Locales: `fr` (default) + `en` at launch, more languages planned later — code should key off `src/i18n/config.ts`'s `locales` array rather than hardcoding a two-way choice (§ Decisions.2, Phase 2.1, Phase 3.2.iii).
2. Locale scope: **fixed per deployment, no per-user override.** The deployment's language comes from a `DEFAULT_LOCALE` runtime env var (not a hardcoded value, not a build-time `NEXT_PUBLIC_` var), consistent with the existing `SITE_URL`/`VAPID_PUBLIC_KEY` runtime-config pattern (commit `554423c`) — same everywhere: UI, emails, push notifications. No cookie, no `profile.locale` DB column, no settings-page language switcher, no per-recipient notification/email translation. Reason (user, 2026-08-11): the app's actual content — post captions, "pronostic" guesses, comments — is user-generated in one language per family, so a per-viewer UI language would mismatch the content anyway; a deployment (== a family) speaks one language.
3. Translation source: AI-drafted first pass for the ~100 files of French copy, reviewed/corrected by the user rather than written from scratch — applies throughout Phase 3.
4. Routing: no URL-based locale routing at all (no `/fr/`/`/en/` prefix, no `[locale]` segment) — locale is resolved once server-side from `DEFAULT_LOCALE`, not per-request. This app has no SEO/shareable-link need for URL-visible locales, and dropping routing removes the `proxy.ts`/Supabase-middleware composition risk and the `next/link`/`useRouter` migration burden entirely.
