## Context

Second of the two big additions (after the calendar, see `.claude/plans/calendar.md`). The whole premise of this app is not posting the baby's photos/info on a public platform — the feed is where that actually happens: admins post photos (baby + trips), everyone with access can react and comment, but **comments must stay siloed by circle** (family never sees friends' comments, and vice versa) even though they're commenting on the same shared post.

Confirmed with the user:
- Posts themselves can *also* be circle-scoped (like events) — an admin can restrict a whole post to one circle, independent of the per-comment siloing.
- Reactions are public across everyone who can see the post (not siloed) — comments are the only thing siloed by circle.
- A post can hold multiple photos (gallery), and needs a separate "date taken" from "date posted" so backdated trip photos land on the right calendar day.
- No edit/delete for comments or reactions in v1 — keep it simple.

This reuses the same visibility primitive as the calendar (`circle_id is null OR circle_id in user's circles`), plus a second, stricter rule for comments specifically. Same architectural constraint applies: **no RLS in this app** — all authorization happens in Server Actions (`assertIsAdmin`, manual `user_id`/`circle_id` filtering), see `.claude/plans/calendar.md`'s "Context" section for the full reasoning.

Existing infra this builds directly on (previously unused, clearly scaffolded for this):
- Per-baby Supabase Storage bucket: `supabase.storage.from(babyId)` (`src/utils/actions/storage.ts`, `src/utils/actions/upload.ts`).
- `useSupabaseUpload` hook + `<Dropzone>` component (`src/utils/actions/use-supabase-upload.ts`, `src/components/dropzone.tsx`) — already supports `maxFiles > 1` for galleries via `multiple: maxFiles !== 1`.
- **Gap found**: no code anywhere creates a Storage bucket when a baby is created (`src/utils/actions/baby.ts` only reads). Confirm a bucket named after the baby's UUID already exists (Supabase Studio) before building this — if not, bucket provisioning needs to be added wherever a baby is actually created, which wasn't found in this codebase (likely manual/seed today, single-baby app).

## Data model

New migration (`mise run db_migration_new create_posts`):

```sql
CREATE TABLE "public"."posts" (
  "id" uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  "created_at" timestamptz DEFAULT now() NOT NULL,      -- when it was actually uploaded
  "baby_id" uuid NOT NULL REFERENCES "public"."babies"("id"),
  "circle_id" uuid REFERENCES "public"."circles"("id"),  -- null = visible to everyone with baby access
  "created_by" uuid DEFAULT auth.uid() NOT NULL REFERENCES "public"."users"("id"),
  "taken_at" date NOT NULL DEFAULT current_date,          -- editable "date taken", drives calendar placement
  "caption" character varying
);

CREATE TABLE "public"."post_photos" (
  "id" uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  "post_id" uuid NOT NULL REFERENCES "public"."posts"("id") ON DELETE CASCADE,
  "storage_path" character varying NOT NULL,  -- e.g. "posts/<post_id>/<filename>" within the baby's bucket
  "position" integer NOT NULL DEFAULT 0,
  "created_at" timestamptz DEFAULT now() NOT NULL
);

CREATE TABLE "public"."post_reactions" (
  "id" bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  "post_id" uuid NOT NULL REFERENCES "public"."posts"("id") ON DELETE CASCADE,
  "user_id" uuid DEFAULT auth.uid() NOT NULL REFERENCES "public"."users"("id"),
  "emoji" character varying NOT NULL DEFAULT '❤️',
  "created_at" timestamptz DEFAULT now() NOT NULL,
  UNIQUE ("post_id", "user_id")  -- one reaction per user per post; changing it is an upsert
);

CREATE TABLE "public"."post_comments" (
  "id" uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  "post_id" uuid NOT NULL REFERENCES "public"."posts"("id") ON DELETE CASCADE,
  "user_id" uuid DEFAULT auth.uid() NOT NULL REFERENCES "public"."users"("id"),
  "circle_ids" uuid[] NOT NULL DEFAULT '{}',  -- snapshot of the commenter's circle memberships at comment time
  "created_at" timestamptz DEFAULT now() NOT NULL,
  "body" character varying NOT NULL
);

-- GRANT ALL ... TO anon/authenticated/service_role for all four tables, matching every existing table.
```

**Design note on `circle_ids` (array, not a single FK)**: a user can belong to more than one circle (`circles_access` has no uniqueness constraint forcing one circle per user). Rather than adding a join table, `post_comments.circle_ids` snapshots all of the commenter's circle memberships at post time, and visibility is checked with Supabase-js's `.overlaps('circle_ids', userCircleIds)`. If in practice every non-admin user only ever ends up in exactly one circle, this degrades to a single-element array — no extra complexity in that common case.

## Server actions

### `src/utils/actions/posts.ts`

- `createPost({ babyId, circleId, takenAt, caption })` — `assertIsAdmin`, insert into `posts`, return the new `id`. Photos are attached in a second step (see Storage flow below) since the upload hook needs a post id for its path first.
- `attachPostPhotos(postId, babyId, filenames: string[])` — `assertIsAdmin`, bulk-insert `post_photos` rows (`storage_path: posts/${postId}/${filename}`, `position: index`), `revalidatePath('/baby/${babyId}/feed')`.
- `getPosts(babyId, { limit, before }: { limit: number; before?: string })` — cursor-paginated feed listing (newest first by `created_at`), joined with `post_photos`. Shared visibility filter (extract as a helper, reusable by `getPostsForRange` below):
  - `getUserCircleIds(babyId)` — same helper introduced in the calendar plan (`.claude/plans/calendar.md`), reused here rather than duplicated.
  - `.eq('baby_id', babyId).or(`circle_id.is.null,circle_id.in.(${circleIds.join(',')})`)`.
- `getPostsForRange(babyId, from, to)` — same visibility filter, filtered by `taken_at` between `from`/`to` instead of cursor-paginated. This is what the calendar page will call to merge posts into its day grid (see `.claude/plans/calendar.md`, "Not building now" section — this closes that gap).
- `deletePost(postId, babyId)` — `assertIsAdmin`, deletes the post row (cascades photos/reactions/comments) and the underlying storage objects via `supabase.storage.from(babyId).remove([...])`.

### `src/utils/actions/reactions.ts`

- `addReaction(postId, babyId, emoji = '❤️')` — requires an authenticated user with `baby_access` to `babyId` (no admin check); upsert on `(post_id, user_id)`.
- `removeReaction(postId, babyId)` — delete own reaction (`user_id = auth.uid()`), no admin check needed since it's scoped to the caller's own row.
- `getReactions(postId)` — no visibility filtering needed (public); returns counts grouped by emoji plus whether the current user has reacted (for toggle UI state).

### `src/utils/actions/comments.ts`

- `addComment(postId, babyId, body)` — requires auth user; call `getUserCircleIds(babyId)`, insert with `circle_ids` set to that snapshot.
- `getComments(postId, babyId)` — `getUserAccess(babyId)` to check `access_level`; if `admin`, return all comments for the post; otherwise filter with `.overlaps('circle_ids', userCircleIds)`.

### Storage flow (photos)

Generalize `src/utils/actions/storage.ts`'s `getImage` (currently hardcodes the `images/${imageId}` path) into a `getSignedUrl(babyId, path)` that takes the full storage path, since post photos live under `posts/<postId>/` rather than `images/`. Client-side create flow:
1. `createPost(...)` server action → returns `postId`.
2. `useSupabaseUpload({ bucketName: babyId, path: `posts/${postId}`, maxFiles: N, allowedMimeTypes: ['image/*'] })` uploads the selected files directly to Storage (existing hook, unchanged).
3. On upload success, `attachPostPhotos(postId, babyId, files.map(f => f.name))` records the DB rows.

## Pages & components

- **New nav entry** (feed has no existing stub, unlike calendar): add `{ id: "feed", name: "Journal", role: "viewer", enabled: true }` to the `pages` array in `src/app/_header/header.tsx`. Consider whether this should be the default/landing page for the baby route — worth a quick decision when implementing, not blocking the plan.
- **`src/app/baby/[babyId]/feed/page.tsx`** (Server Component): `getUserAccess(babyId)` for `isAdmin`, first page of `getPosts(babyId, { limit: 10 })`, renders a `<PostCard>` per post inside a `Suspense` boundary (matches the pattern in `guess/page.tsx`).
- **`post_card.tsx`**: photo gallery (grid if 1–2 photos, swipeable/scrollable strip if more), caption, `taken_at` formatted with `date-fns`, a reaction bar (heart button + count, click toggles `addReaction`/`removeReaction` optimistically), and a comment list + input below. This component is written to be reusable from the calendar's day-detail sheet too (per the calendar plan's integration note), so it shouldn't assume it's rendered inside the feed's own scroll container.
- **`comment_list.tsx`** + **`comment_input.tsx`**: simple flat list (no threading/replies in v1), newest last; input calls `addComment` then `router.refresh()`.
- **`create_post_modal.tsx`** (admin-only): modeled on `guess/_components/modal.tsx`'s open/close + form pattern — `<Dropzone>`/`<DropzoneContent>`/`<DropzoneEmptyState>` wired to `useSupabaseUpload` for the gallery, a caption `textarea`, a `taken_at` date input (defaults to today), and a circle `Select` (same "visible par tout le monde" + per-circle options pattern as the calendar's create-event modal, from `getCircles(babyId)`).
- Infinite scroll or a simple "Charger plus" button for pagination via `getPosts`'s `before` cursor — a button is less code and fine for v1 given expected volume (family photos, not a public feed).

## Calendar integration (closes the loop from the calendar plan)

- `calendar_view.tsx` (already planned to be written against a per-day bucket) calls `getPostsForRange(babyId, from, to)` alongside `getEvents`, merges both into the same per-day list.
- Day cells show a small thumbnail (first photo) for days with posts, distinct from the event dots/milestone icons.
- Clicking a day with a post opens the same `day_detail_sheet.tsx`, rendering the shared `post_card.tsx` for post entries alongside plain event rows — no duplicate post-rendering logic.
