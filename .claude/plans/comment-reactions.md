# Réactions sur les commentaires (emoji reactions on comments)

Add the same 5-emoji reaction picker that already exists on posts
(🍼 Biberon, 👶 Bébé, 😴 Dodo, 🎉 Célébration, ❤️ Cœur) to individual
comments, so users can react to a comment instead of only to the post
itself. One reaction per user per comment, swappable — identical
semantics to post reactions.

## Scope decisions (confirmed with user)

- Full emoji picker (not a single like/heart toggle) — reuses the existing
  `REACTIONS` constant and matches the post-level UX so the app has one
  consistent reaction vocabulary.
- Push notification included: the comment's author gets a `new_comment_reaction`
  notification when someone reacts to their comment (self-reactions skipped),
  mirroring `new_reaction` on posts.
- No independent per-comment data fetch on mount. `reaction_picker.tsx` (post
  level) gets its initial data via an `initialReactions` prop and only
  self-fetches *after* a pick. For comments we go one step further and drop
  even that self-fetch: `CommentList` already refetches the whole comment
  list via a parent-supplied `onChanged` callback after every edit/delete, so
  the new comment-level picker reuses that same callback after a reaction
  mutation instead of calling `getReactions` itself. This means comment
  reaction data must be attached server-side to each `Comment` (in
  `getComments`/`getCommentsForPosts`), the same way `nickname` already is.
- No DB-level RLS — this app has none anywhere (enforcement lives in the
  server-action layer via `getUserAccess`); `comment_reactions` follows the
  same `GRANT ALL` + app-layer-check pattern as `post_reactions`.

## Existing infra (reused as-is)

- `REACTIONS` constant (`src/utils/reactions.ts`) — same 5 emojis, same
  `reactions.<key>` i18n labels.
- `post_reactions` table + `src/utils/actions/reactions.ts` — the exact
  schema/action shape to mirror (`emoji varchar default '❤️'`, unique
  `(post_id, user_id)`, `addReaction`/`removeReaction`/`getReactions`/
  `getReactionsForPosts`).
- `post_comments` table + `src/utils/actions/comments.ts` — ownership/circle
  visibility logic is untouched; we only add a field to what `getComments`
  returns.
- `notifyUsers(babyId, type, content, targetUserIds)` push helper
  (`src/utils/actions/notify.ts`).
- UI primitives from `reaction_picker.tsx` (`Popover`, `cn`, `SmilePlus`
  icon, the pill-with-popover-of-names pattern).

## Changes

1. `supabase/migrations/20260826120000_create_comment_reactions.sql` (new):
   ```sql
   CREATE TABLE "public"."comment_reactions" (
     "id" bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
     "comment_id" uuid NOT NULL,
     "user_id" uuid DEFAULT auth.uid() NOT NULL,
     "emoji" character varying DEFAULT '❤️' NOT NULL,
     "created_at" timestamptz DEFAULT now() NOT NULL
   );
   ALTER TABLE ONLY "public"."comment_reactions" ADD CONSTRAINT "comment_reactions_pkey" PRIMARY KEY ("id");
   ALTER TABLE ONLY "public"."comment_reactions" ADD CONSTRAINT "comment_reactions_comment_id_user_id_key" UNIQUE ("comment_id", "user_id");
   ALTER TABLE ONLY "public"."comment_reactions" ADD CONSTRAINT "comment_reactions_comment_id_fkey" FOREIGN KEY ("comment_id") REFERENCES "public"."post_comments"("id") ON DELETE CASCADE;
   ALTER TABLE ONLY "public"."comment_reactions" ADD CONSTRAINT "comment_reactions_user_id_fkey" FOREIGN KEY ("user_id") REFERENCES "public"."users"("id") ON DELETE CASCADE;
   GRANT ALL ON TABLE "public"."comment_reactions" TO "anon", "authenticated", "service_role";

   ALTER TYPE "public"."notification_type" ADD VALUE 'new_comment_reaction';
   ```
   (mirrors `post_reactions`, cascade-deletes with the comment; follows the
   `create_stories.sql`/`create_anecdotes.sql` precedent of adding a new
   `notification_type` enum value in the same migration that introduces the
   feature that uses it.)

2. Regenerate `src/utils/supabase/database.types.ts` via
   `mise exec -- supabase gen types typescript --local > src/utils/supabase/database.types.ts`
   (or the project's existing `mise run` task if one wraps this) after
   applying the migration, per the tooling rule in `CLAUDE.md`.

3. `src/utils/actions/comment_reactions.ts` (new), mirroring
   `reactions.ts` one-for-one:
   - `addCommentReaction(commentId: string, postId: string, babyId: string, emoji: string = '❤️')`
     — auth + `getUserAccess` check, `upsert` onConflict `'comment_id,user_id'`,
     `revalidatePath`, then looks up the comment's `user_id` and sends a
     `new_comment_reaction` notification to that user (skipped if reacting to
     your own comment).
   - `removeCommentReaction(commentId: string, postId: string, babyId: string)`
     — delete by `comment_id` + `user_id`, `revalidatePath`.
   - `getCommentReactionsForComments(commentIds: string[], babyId: string): Promise<Record<string, ReactionsData>>`
     — batched fetch (same shape as `getReactionsForPosts`), reused by
     `comments.ts` below. A non-batched single-comment `getCommentReactions`
     is not needed since the picker never self-fetches (see scope decision).

4. `src/utils/actions/comments.ts`: `getComments` and `getCommentsForPosts`
   each call `getCommentReactionsForComments` (in the existing
   `Promise.all` alongside the nicknames fetch) and attach the result as a
   `reactions: ReactionsData` field on every returned comment, the same way
   `nickname` is already attached. `Comment` (inferred from `getComments`'s
   return type) picks up the new field automatically — no change needed in
   `src/utils/actions/posts.ts`, since `PostWithDetails.comments: Comment[]`
   already flows through.

5. `src/app/baby/[babyId]/feed/_components/comment_reaction_picker.tsx`
   (new): near-identical to `reaction_picker.tsx` but scaled down for the
   tighter comment layout (smaller trigger/emoji buttons, no separate
   "total count" styling difference needed) and props-driven instead of
   self-fetching:
   ```ts
   { commentId, postId, babyId, initialReactions, onChanged }: {
     commentId: string; postId: string; babyId: string
     initialReactions: ReactionsData; onChanged: () => void
   }
   ```
   On pick: call `addCommentReaction`/`removeCommentReaction`, then call
   `onChanged()` instead of `setReactions(await getReactions(...))` — the
   parent's refetch (`loadComments`) will bring back fresh `comment.reactions`
   for every comment. Local `pending`/`pickerOpen` state only, no local
   `reactions` state.

6. `src/app/baby/[babyId]/feed/_components/comment_list.tsx`: render
   `<CommentReactionPicker commentId={comment.id} postId={comment.post_id} babyId={babyId} initialReactions={comment.reactions} onChanged={onChanged} />`
   under each comment's body text (comments already receive `onChanged` as a
   prop, used today for edit/delete — no new prop threading needed).

7. `src/utils/notification-types.ts`: add `'new_comment_reaction'` to
   `ALL_NOTIFICATION_TYPES` so it shows up as a toggleable preference in
   `baby_settings_card.tsx` (it's not admin-only, so it does not go in
   `ADMIN_ONLY_TYPES`).

8. `messages/en.json` and `messages/fr.json`: add
   `pushNotifications.newCommentReaction.{title,body}` (same `{name}`/`{emoji}`
   placeholders as `newReaction`) and a `notificationTypes.new_comment_reaction`
   label, in both locales.

## Out of scope / not doing

- No Supabase Realtime / SSE relay wiring — `comment_reactions` stays out of
  `realtime-relay.ts`'s table whitelist, same as `post_comments` and
  `post_reactions` today; updates propagate via the existing
  mutate → `revalidatePath` + `onChanged` refetch pattern.
- No comment-level reaction breakdown in `post_stats_modal.tsx` — it keeps
  showing a raw `commentCount`, matching its current minimal treatment of
  comments (only post-level reactions get a name breakdown there today).
- No RLS — matches the rest of the schema.
- No reactions on any other content type (events/milestones/polls) — comments
  only, same boundary as the original `doudou-reactions.md` change.
